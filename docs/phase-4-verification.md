# Phase 4 verification (SAN-48)

Verified against the local Supabase with the seeded admin, operator, treasurer and read-only users. The live acceptance suite is `tests/integration/phase-4-acceptance.test.ts`. It calls the real SvelteKit loads and actions for `/campaigns/[id]/bonds/import`, `/campaigns/[id]/bonds/import/[sessionId]` and `/campaigns/[id]/bonds/scan`, which use the real import services and SQL functions. Every criterion creates its own campaign (`[it-p4 <run id>] …`).

## Known gaps

- **SAN-100, server trusts the client's base number.** `import_session_add_items` stores the `base_number` the client sends. In `manual_mapping`, and in a pattern mode without a pattern, nothing on the server derives or checks it, so a wrong `numero_base` in a file becomes a valid row with the wrong number. Criterion 2 was verified with that limitation (the suite sends the right number). Scans resolve the code in SQL; corrections (`import_session_update_item`, SAN-46) re-check the code against the number.
- **SAN-100, `duplicate_number` is never produced.** Every repeated number is reported as `number_conflict`; the Duplicates metric counts those rows.
- **pgTAP and the shared local database.** See the pgTAP row below.

## Test data and re-runs

The suite never deletes campaigns, sessions, items, bonds or numbers. `RUN_ID` combines a timestamp and a UUID; campaigns are named `[it-p4 <run id>] …` and request ids use the `it-p4-<run id>` prefix. Assertions only query the sessions and campaigns the running suite created.
