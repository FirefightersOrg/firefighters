# Phase 3 verification (SAN-27)

Verified on the local development environment (macOS, Node 24.12.0, pnpm 11.17.0, Supabase CLI 2.108.0), with the local stack reset from this branch: 10 migrations, Phase 3 being `20261119000000_bonds.sql` (SAN-22), `20261120000000_bond_rpcs.sql` (SAN-23) and `20261121000000_bond_list_view.sql` (SAN-26), i.e. the SAN-22 → SAN-23 → SAN-24 → SAN-25 → SAN-26 stack.

The live checks are in `tests/integration/phase-3-acceptance.test.ts` (23 tests). They run the real code paths against local Supabase with the seeded users (admin, operator, treasurer, collector, read-only):

- the SvelteKit loads and form actions of `/campaigns/[id]/bonds` (list), `/bonds/new` (simple bond), `/bonds/pata/new` (`?/printed`, `?/group`), `/bonds/[bondId]` (record, `?/ungroup`, `?/annul`) and `/campaigns/[id]` (`?/rules`), called with a **user-scoped** client and the caller's real permission list (`my_permissions()`), like the Phase 1 and 2 suites;
- the audited SQL functions (`bond_create`, `bond_group_into_pata`, `bond_ungroup_pata`, `bond_annul`, `campaign_*`) through the same client, when the database check itself is the point (SQLSTATE, message, DETAIL);
- server-side rendering (`svelte/server`) of the list and record pages with the data their loads returned for each role.

Every mutation is checked by its `request_id`: one successful call → exactly one `audit_log` row with the expected action, entity, actor, old/new values and reason; one rejected call (route or database) → no row.

## Test data and re-runs

Bonds, campaigns and their history cannot be deleted (no DELETE privilege for any API role, plus delete/truncate triggers). Every campaign the suite creates is named `[it-p3 <run id>] …` and every request id starts with `it-p3-<run id>-`; assertions only look at the run's own campaigns, bonds and request ids, and numbers are unique per campaign, so the suite runs again without a reset. The browser smoke tags its campaigns `[it-p3-smoke …]`.

```sql
select id, name, status from public.campaigns where name like '[it-p3 %' order by created_at;
select action, entity_id, request_id from public.audit_log where request_id like 'it-p3-%' order by created_at;
```

## Not verified here

- **Real sales.** Nothing in Phase 3 sells a bond: the "annulled from sold keeps its numbers" case is set up by `service_role` writing the status changes directly (the database guards apply; there is no audit row for those writes). The sale and its annulment flows arrive in Phases 4–10.
- **Hooks / cookies.** Loads and actions get `locals` built by the test, not by `hooks.server.ts` (covered by unit tests and by the browser smoke).
- **Grouping UI with several people at once.** Concurrency is exercised at the database (two simultaneous `bond_create` / `bond_group_into_pata` calls); the grouping page keeps its selection in the URL and the database re-checks under lock.
- **JavaScript off.** The forms post without `enhance` (unit/render tests), but the browser smoke ran with JavaScript on.
- **Phase 4 barcode modes and `created` bonds.** Bonds start `available`; `created` and barcode-driven entry are Phase 4.

## Bugs found

- **Bonds list page past the last one → 500** (#28, fixed on `santiagomusso/san-26-build-bond-detail-and-list-views`, 0196d15): PostgREST answers a range starting after the last matching row with `PGRST103` (416, "Requested range not satisfiable"), and the list load turned it into "Could not load the bonds" (500), e.g. for `?page=999` or a stale link after bonds were annulled/filtered. `listBonds` now returns no entries and reads the total with a second query, so the page renders "Page N of M" with a link back. Unit test in `repositories/bonds.test.ts`; covered live in §5 and by the browser smoke.

Observation (not changed): on a page past the last one the pagination shows "Page 99 of 2" with a "Previous" link to page 98 rather than to the last page.
