# Phase 2 verification (SAN-21)

Verified on the local development environment (macOS, Node 24.12.0, pnpm 11.17.0, Supabase CLI 2.108.0), with the local stack reset from this branch (migrations up to `20261118000000_commission_rules.sql`, i.e. the SAN-16 → SAN-18 → SAN-17 → SAN-19 → SAN-20 stack).

The live checks are in `tests/integration/phase-2-acceptance.test.ts` (46 tests). They run the real code paths against local Supabase with the seeded users (admin, operator, treasurer, collector, read-only):

- the SvelteKit loads and form actions of `/campaigns`, `/campaigns/new`, `/campaigns/[id]` and `/campaigns/[id]/commissions`, called with a **user-scoped** client and the caller's real permission list (`my_permissions()`), the same way the Phase 1 suite calls `POST /api/admin/users`;
- the audited SQL functions (`campaign_*`, `commission_rule_*`) directly through the same user-scoped client, when the point is the database check itself (SQLSTATE).

Every mutation is checked by its `request_id`: one successful call → exactly one `audit_log` row with the expected action, entity, actor, old/new values and reason; one rejected call → no row.

## Test data and re-runs

Campaigns and commission rules cannot be deleted (no DELETE privilege for any API role, plus delete/truncate triggers), and the suite does not weaken that. Instead:

- every campaign it creates is named `[it-p2 <run id>] …` and every request id starts with `it-p2-<run id>-` (the run id is a UTC timestamp plus a random suffix, printed at the start of the run);
- assertions only look at the run's own entities and request ids, and the overlap constraint is per campaign, so the suite runs again without a reset;
- the data stays in the local database. To inspect or drop it, use SQL as the owner or `supabase db reset` (which wipes everything; re-run `pnpm seed:admin` afterwards):

```sql
select id, name, status from public.campaigns where name like '[it-p2 %' order by created_at;
select action, entity_type, request_id from public.audit_log where request_id like 'it-p2-%' order by created_at;
```

The suite never runs `supabase db reset` itself.

## Running the integration suites

```sh
supabase start
supabase db reset
APP_ENV=local pnpm seed:admin   # needs PUBLIC_SUPABASE_URL / SUPABASE_SERVICE_ROLE_KEY, e.g. from `supabase status -o env`
APP_ENV=local pnpm test:integration
```

Configuration and the local-only guard are the Phase 1 ones (`tests/integration/local-env.ts`, `global-setup.ts`, see `docs/phase-1-verification.md`).

## Not verified here

- **Permission split at the database level with a real non-admin role.** No seeded role holds `campaign.close` without `campaign.update_rules` (or the reverse), and the role catalog only changes through migrations, so the integration suite checks that split at the route gate (admin with a trimmed `locals.permissions`). The database-level split (activation needs `campaign.update_rules`, closing/annul need `campaign.close`) is covered by pgTAP `006` with transaction-scoped test roles.
- **`active → annulled`** is not exercised live (draft → annulled is); covered by pgTAP `005`/`006`.
- **Hooks / cookies.** Loads and actions get `locals` built by the test (user-scoped client, real `my_permissions()`), not by `hooks.server.ts`; the hook is covered by unit tests and by the browser smoke above.
- **Special collector commission rules** (`applies_to_collector_id`) do not exist yet (Phase 5 / 9).
- **Truly simultaneous requests.** Concurrent edits are tested sequentially (B saves, then A submits the form it loaded before B's save), which is the case optimistic concurrency guards; two requests racing inside the same instant are serialized by the row locks (`FOR UPDATE` / `FOR SHARE`) and not exercised live.

## Bugs found

The first verification found none. A later review of the stack found four, fixed in the lower PRs and covered here (criterion 10):

- **NaN amounts** (#19, #22): Postgres `numeric` accepts `'NaN'`, and NaN compares greater than every number and equal to itself, so it passed `simple_bond_value > 0`, the exact-installment CHECK and `fixed_amount > 0`. The CHECKs now exclude NaN, and `commission_rule_validate` rejects NaN and ±Infinity with 22023.
- **Unbounded `number_digits`** (#19, #18): capped at 10 (`max_number` is an integer), in the table and in `validateNumberingConfig` (`MAX_NUMBER_DIGITS`).
- **Lost updates** (#20, #22): two people editing the same campaign or rule silently overwrote each other. `campaign_update`, `campaign_update_rules` and `commission_rule_update` now require the `updated_at` the caller loaded.
- **Why `PT409` and not `40001`**: the conflict was first raised as `40001` (`serialization_failure`). Against the live stack a stale save never returned: PostgREST retries a transaction that fails with `40001` automatically and without limit, so the request hung and PostgREST kept re-running the function (hundreds of thousands of errors in minutes, until `supabase_rest_firefighters` was restarted). pgTAP did not catch it because it calls the functions without PostgREST. The functions now raise `PT409`, PostgREST's custom-status SQLSTATE: HTTP 409 with code `PT409`, never retried (a stale call returns in a few milliseconds).
